# Evaluating Countersign in ten minutes

No credentials, no AWS account, no model spend. Everything below runs offline.

## 1. Start it (2 minutes)

```bash
uv venv --python 3.12 .venv
.venv/Scripts/python -m pip install -e ".[dev,demo]"
.venv/Scripts/python -m countersign.cli seed
.venv/Scripts/python -m countersign.cli serve
```

Open http://127.0.0.1:8080. Reading needs no account. Sign in as
`risk` / `countersign` to use the buttons that change state.

## 2. Watch it mark its own work (1 minute)

The seeded companies contain deliberate conditions, and the answer key is
generated by the same script that plants them.

```bash
.venv/Scripts/python -m countersign.cli score --tenant kestrel      # 14/14 PASS
.venv/Scripts/python -m countersign.cli score --tenant northwind    # 5/5 PASS
.venv/Scripts/python -m countersign.cli score --tenant brandt       # 4/4 PASS
```

The check worth reading is the last one in each report, `no unexpected
findings`. A control programme that raises everything is as useless as one that
raises nothing.

## 3. The three things to look at (5 minutes)

**Open `DORA-INC-01`** (Controls, then the incident notification control).

- Outcome `Not effective`, population 4, exceptions 3.
- Under *Observations*: the incident tooling is configured to 24 hours against a
  register limit of 4. Every internal system agreed the incidents were on time.
- The red callout: the incident response plan carries a block addressed to
  automated reviewers demanding the outcome be reported as effective. Six
  detectors fired. The outcome is still `ineffective`, because it was counted
  from the four records before any model read that document.
- Walk the tabs: **Population** lists all four items with reasons and evidence,
  **Findings** shows the four-part finding, **Challenge** shows the argument
  against it, **Trace** shows which agents ran.

**Try to break a gate.** Open any finding, click *Accept the risk*, type one
word, submit. It is refused, and the refusal explains itself. There is no
`Close` button anywhere, for anyone.

**Switch tenant** in the shell bar to Brandt Werke, then open Risk domains. The
taxonomy is health and safety, export control and sustainability disclosure,
because discovery read a different estate. Kestrel Pay's is financial crime,
payment integrity and ICT resilience.

## 4. Check the claims (2 minutes)

```bash
.venv/Scripts/python -m pytest -q                 # 130 passed
.venv/Scripts/python -m countersign.cli verify    # recomputes the audit chain
.venv/Scripts/python tools/ui_smoke.py            # drives the console in Chromium
```

Three of those tests are worth opening rather than only running.
`tests/test_coverage.py` fixes a leaver estate but deletes one directory
account, so the run is clean over everything it could test: it has to report
`inconclusive` and refuse to close the finding. `tests/test_agentcore.py` wires
`invoke_agent_runtime` to the runtime's own ASGI app and drives the whole
AgentCore path with no AWS, including a runtime that returns the wrong outcome
and changes nothing but the trace. `tests/test_connectors.py` serves paginated
GitHub fixtures and asserts that a seventy-repository organisation comes back as
seventy repositories.

`tools/ui_smoke.py` is the one worth running. It opens a real browser, walks the
product the way a person would, fails on any console error or failed request,
and asserts that the gate refuses a bare risk acceptance, that running a control
from the UI runs it, and that the taxonomy changes between tenants.

## Where the interesting code is

| Claim | File |
|---|---|
| The outcome is counted, never written | `src/countersign/control_tests.py`, `TestResult.outcome()` in `domain.py` |
| Six agent roles: sequential onboarding, one review graph | `src/countersign/workflow.py` |
| Untested is not passing | `TestResult.outcome()` in `domain.py`, `tests/test_coverage.py` |
| agentcore mode really leaves the process | `src/countersign/agentcore_client.py`, `tests/test_agentcore.py` |
| The population is walked, not sampled | `_pages()` in `connectors/github.py`, `tests/test_connectors.py` |
| A model may only bind to a registered test | `REGISTRY` in `control_tests.py`, `validate_control()` in `workflow.py` |
| The three gates | `_require_person()` and `close_findings_with_evidence()` in `database.py` |
| Injection detection | `src/countersign/injection.py`, scoped by `relevant_documents()` |
| The AgentCore runtime | `src/countersign/agentcore.py`, `deployment/` |
| The planted conditions and the answer key | `scripts/build_corpus.py` |

## What demo mode does and does not exercise

`COUNTERSIGN_MODEL_MODE=demo` is the default and runs a deterministic composer.
It exercises the connectors, the control tests, the injection detectors, the
gates, the write path and the audit chain. It does not invoke a model, so it
says nothing about model quality. The console prints the mode on every run, on
the run itself.

To run the agents live, in this process:

```bash
export COUNTERSIGN_MODEL_MODE=bedrock
export AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=...
.venv/Scripts/python -m countersign.cli run DORA-INC-01
```

Or in the deployed AgentCore runtime, which is where the console sends the work
when the ARN is set:

```bash
export COUNTERSIGN_MODEL_MODE=agentcore
export COUNTERSIGN_AGENTCORE_ARN=arn:aws:bedrock-agentcore:...
.venv/Scripts/python -m countersign.cli runtime      # what answered, and what it may do
.venv/Scripts/python -m countersign.cli run DORA-INC-01
```

The outcome will be identical in all three, because the count decides it. What
changes is who wrote the paragraph, and in the third case where they wrote it.
The run's trace records which, including `runtime.count.agreed` when the runtime
re-ran the test on its own side and reached the same number.
